# 工具安全控制「自然语言配置层」设计方案

> 状态：设计稿（待评审）
> 目标：让「最小权限机制的建立」本身也能通过自然语言多轮交互完成，策略可持久化、可复用，
> 第三方智能体接入后可逐步配置出自己的安全边界，而不需要改代码。

## 1. 背景与问题

当前实现完成了**运行期**安全：`ToolGateway` 的五道闸门对每一次工具调用强制执行
（工具白名单 → 目录白名单 → 危险确认 → 最小权限 → 命令白名单），但这套策略是**代码里静态写死的**。

遗留缺口是**配置期**：用户无法在不改代码的前提下，用自然语言「告诉」系统：

- 这个工具允不允许用、属于什么风险等级；
- 允许访问哪些目录、哪些命令；
- 在什么场景下限制使用某个工具。

本方案回答一个问题：**如何把「配置安全策略」变成智能体可被自然语言驱动的能力，并守住
「谁有权改权限」这一元级安全边界。**

## 2. 核心分层：运行期 vs 配置期

| 层次 | 职责 | 现状 |
|------|------|------|
| 运行期 | 对每次工具调用强制校验 | ✅ 已实现（`gateway.py`） |
| 配置期 | 通过自然语言交互生成/修改安全策略 | ❌ 待实现（本方案） |

两者通过**持久化策略文件**连接：配置期写入策略 → 运行期启动时加载策略。

## 3. 接入契约（第三方智能体接入时需提供）

「工具安全控制」要能自动为智能体所有工具建立权限，前提是它能「读懂」这些工具。
因此接入方需提供最小信息集：

1. **工具清单 + 自然语言描述**：每个可调用工具至少一句 `description`（它做什么）。
   → 对应现有 `registry.py` 的 `TOOL_REGISTRY` / `Tool.description`。
2. **参数说明（推荐）**：`params_desc`，用于 LLM 准确抽取参数和展示给用户确认。
   → 对应 `Tool.params_desc`。
3. **目录白名单初始范围**：文件类工具允许访问的根目录。
   → 对应 `DirectoryPolicy`。
4. **确认回调**：`confirm_fn`，用于授权「改权限」这类高敏动作。
   → 对应 `AgentConfig.confirm_fn`。

> 没有 `description` 的工具，配置层无法展示、无法自动推导风险，只能按「默认拒绝」处理。

## 4. 自然语言如何触发

**不做单独的「模式检测」**。把配置动作本身注册成工具，走与 `read_file` 完全相同的 LLM 路由：

| 配置工具 | 自然语言触发示例 | 作用 |
|----------|------------------|------|
| `configure_tools` | 「我希望对现有工具做安全控制/权限划分」 | 进入配置向导，逐项确认 |
| `set_tool_policy` | 「读取文件时限制用 read_file」「禁止删除」 | 设置单工具允许/禁止与风险 |
| `add_directory_whitelist` | 「只允许访问 data 目录」 | 增删目录白名单 |
| `set_max_risk` | 「这个会话只给只读权限」 | 设置会话最小权限上限 |
| `add_command_whitelist` | 「只允许 ls 和 echo」 | 增删命令白名单 |

这些工具同样是「配置层的能力」，调用时同样要经过 `ToolGateway`——只是它们的参数会被
解析成对策略文件的修改，而非直接执行危险动作。

## 5. 多轮交互配置流程（确认向导）

以 `configure_tools` 为例，配置是**对话式、逐步确认**的：

```
用户：「我希望对现有工具做安全控制」
  → 路由到 configure_tools
  → 展示工具清单（含 description / 当前风险 / 当前是否允许）
  → 逐个询问：「read_file（读取文件）→ 允许？[y/N] 风险等级？[low/medium/high]」
  → 每项用户确认后，暂存到会话草稿
  → 全部完成后，统一展示差异并请求最终确认
  → 用户确认 → 写入 policy 文件 → 审计日志记录本次配置变更
```

关键原则：**每个修改动作都要用户确认**，不静默改权限。

## 6. 策略持久化格式

`policy.json`（放在白名单之外，与审计日志同级，如 `config/policy.json`）：

```json
{
  "version": 1,
  "max_risk": "high",
  "auto_approve": false,
  "tool_policies": {
    "read_file":   { "allowed": true,  "risk": "low" },
    "write_file":  { "allowed": true,  "risk": "medium" },
    "delete_file": { "allowed": false },
    "run_command": { "allowed": false }
  },
  "directory_whitelist": ["data"],
  "command_whitelist": ["ls", "echo", "pwd"],
  "confirm_required": ["write_file", "delete_file", "run_command"]
}
```

启动时加载，覆盖代码内默认值；运行期 `ToolGateway` 按此策略执行。

## 7. 元级安全约束（最重要）

「改权限」本身是最高风险动作，必须独立设防：

1. 所有配置工具 `requires_confirmation = True`。
2. 配置工具**强制走 `confirm_fn`**，`auto_approve` 对它们**不生效**（否则智能体可静默给自己开权限）。
3. 配置变更必须写审计日志（谁、何时、改了什么），可回溯。

即：**智能体可以『建议』权限，但「落盘生效」必须经过用户确认。**

## 8. 落地步骤

- **M1**：定义 `Policy` 数据结构 + `policy.json` 读写（`agent/policy_store.py`）。
- **M2**：注册配置工具，接入 LLM 路由与关键词路由。
- **M3**：实现多轮确认向导（`configure_tools` 对话式流程）。
- **M4**：`ToolGateway` 启动时加载 `policy.json`，替代写死的默认策略。
- **M5**：配置变更审计 + 测试（含「智能体不能绕过确认改权限」的负向用例）。

## 9. 与现有代码的映射

| 现有模块 | 在配置层中的角色 |
|----------|------------------|
| `registry.py` | 配置工具与业务工具的**统一登记处**，是工具清单来源 |
| `gateway.py` | 运行期加载策略并强制校验（M4 改造点） |
| `agent.py` | 路由配置工具的入口（自然语言 → 配置工具） |
| `audit.py` | 记录配置变更，实现「可回溯」 |
| `guard.py` | 配置工具的确认闸门（confirm_fn 强制生效） |
